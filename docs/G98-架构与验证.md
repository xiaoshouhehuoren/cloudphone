# G98 云手机 · 摄像头注入架构与验收（2026-11）

## 1. 分层

```
浏览器 / 手机 App
   │  WebRTC(WHEP) 看屏 · HTTP(JSON) 控制 · 上传素材
   ▼
g98-dashboard (console3.py, :8099 HTTP / :8443 HTTPS)
   ├── /api/rtc/*    屏幕推流（screenrecord → frame_pump → ffmpeg → mediamtx）
   ├── /api/cam/*    相机注入（转调 camd，必要时重建相机会话）
   └── /m, /         移动页 / 桌面三栏控制台
   ▼
g98-camd (:8100)  ── 每个实例两个 v4l2loopback 节点，热切换 idle/图片/视频/RTSP
   ▼
ReDroid 容器 wx1..wx5
   └── camera.provider@2.4-service → camera.mt6983.so（V4L2 HAL）→ /dev/video2x
```

## 2. 已修复的三个根因

1. **HIDL HandleImporter 空实现**（最致命）：CameraDeviceSession 的 mCirculatingBuffers 缓存 importBuffer
   返回的指针，旧的空实现把 HIDL 事务内的临时 native_handle 直接留下，事务结束即悬空。
   后续帧交给 HAL 时 version/numFds/numInts 全是垃圾 → `native_handle_clone` 失败、gralloc lock -22、
   provider 空转、CameraServiceWatchdog abort、App 报 "Can't connect to the camera"。
   现在 `HandleImporter_custom.cpp` 做 native_handle_clone + gralloc registerBuffer，freeBuffer 做
   unregisterBuffer + close + delete。
2. **native_handle_clone 后没 close fd**：provider fd 每秒涨 ~29 个。`capture_request.cpp` /
   `arc/frame_buffer.cpp` 的析构改为先 native_handle_close 再 native_handle_delete。
3. **DequeueRequest 两条自旋路径**：v4l2loopback 的 DQBUF 立即返回 EAGAIN，原实现不 sleep；
   且「dequeued buffer 无 pending request」直接丢帧不还队列，fd 永远 POLLIN 就绪。
   现在 poll(50ms) 等待，丢弃前 VIDIOC_QBUF 还回并 usleep(2ms)。五台 provider CPU 从各 ~90% 降到 ~1.6%。

## 3. 每实例独立节点（P2）

- v4l2loopback 编到 `MAX_DEVICES=16`（源码默认 8，12 节点 modprobe 会 EINVAL）
- `devices=12 video_nr=20..31 exclusive_caps=1 max_buffers=8`，wxN 用 20+2(N-1) / +1
- 容器启动时写 `vendor.camera.redroid.nodes`，HAL 据此打开节点，五个实例互不抢设备
- camd 常驻持有节点写端、恒定 YU12:640x480，切源只换 reader，最后帧保留，切源 <150ms

## 4. UI

- 桌面（/）：左实例列表、中 stage（WebRTC 实时画面）、右 inspector；工具栏「相机」「定位」抽屉。
  相机抽屉的节点下拉按当前实例动态生成（后置/前置 · /dev/videoNN）。
- 移动（/m）：全屏画面 + 底部工具栏；「◉相机」打开 Bottom Sheet（手机实时 / 图片 / 视频 + 前后置 + 恢复空闲），
  上传后热注入，不重启相机、不重启 provider。

## 5. 验收

`tests/verify_camera_e2e.py` 每台检查：节点是字符设备、节点属性、devices=2、注入纯红图后中心像素、
watchdog=0、Device 0 打开。最近一次全量：**5/5 PASS**（注入延迟 1.0–2.1s，像素 (253,0,0)）。
