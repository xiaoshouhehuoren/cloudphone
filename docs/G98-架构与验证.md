# G98 云手机 · 摄像头注入架构与验收（2026-11）

## 1. 分层

```
浏览器 / 手机 App
   │  WebRTC(WHEP) 看屏 · HTTP(JSON) 控制 · 上传素材
   ▼
g98-dashboard (console3.py, :8099 HTTP / :8443 HTTPS)
   ├── /api/rtc/*    屏幕推流（screenrecord → frame_pump → ffmpeg → mediamtx）
   ├── /api/cam/*    相机注入（转调 camd，必要时重建相机会话）
   └── /m, /         移动页 / 桌面三栏控制台
   ▼
g98-camd (:8100)  ── 每个实例两个 v4l2loopback 节点，热切换 idle/图片/视频/RTSP
   ▼
ReDroid 容器 wx1..wx5
   └── camera.provider@2.4-service → camera.mt6983.so（V4L2 HAL）→ /dev/video2x
```

## 2. 已修复的三个根因

1. **HIDL HandleImporter 空实现**（最致命）：CameraDeviceSession 的 mCirculatingBuffers 缓存 importBuffer
   返回的指针，旧的空实现把 HIDL 事务内的临时 native_handle 直接留下，事务结束即悬空。
   后续帧交给 HAL 时 version/numFds/numInts 全是垃圾 → `native_handle_clone` 失败、gralloc lock -22、
   provider 空转、CameraServiceWatchdog abort、App 报 "Can't connect to the camera"。
   现在 `HandleImporter_custom.cpp` 做 native_handle_clone + gralloc registerBuffer，freeBuffer 做
   unregisterBuffer + close + delete。
2. **native_handle_clone 后没 close fd**：provider fd 每秒涨 ~29 个。`capture_request.cpp` /
   `arc/frame_buffer.cpp` 的析构改为先 native_handle_close 再 native_handle_delete。
3. **DequeueRequest 两条自旋路径**：v4l2loopback 的 DQBUF 立即返回 EAGAIN，原实现不 sleep；
   且「dequeued buffer 无 pending request」直接丢帧不还队列，fd 永远 POLLIN 就绪。
   现在 poll(50ms) 等待，丢弃前 VIDIOC_QBUF 还回并 usleep(2ms)。五台 provider CPU 从各 ~90% 降到 ~1.6%。

## 3. 每实例独立节点（P2）

- v4l2loopback 编到 `MAX_DEVICES=16`（源码默认 8，12 节点 modprobe 会 EINVAL）
- `devices=12 video_nr=20..31 exclusive_caps=1 max_buffers=8`，wxN 用 20+2(N-1) / +1
- 容器启动时写 `vendor.camera.redroid.nodes`，HAL 据此打开节点，五个实例互不抢设备
- camd 常驻持有节点写端、恒定 YU12:640x480，切源只换 reader，最后帧保留，切源 <150ms
- **静态源不常驻 ffmpeg**：idle/image 只解码一帧（`-frames:v 1`）缓存为 460800 字节缓冲，
  写线程按 30fps 原样重复写该缓冲。之前每节点一个 30fps ffmpeg，10 个节点吃 0.5–1.5 核，
  宿主 load 一度 9；改后 testsrc2 ffmpeg 归零，camd 整体 CPU 5–6%，load 回到 5 左右，
  节点仍按满速喂帧（HAL 的 5s watchdog 不会因为空闲而触发）。

## 尺寸/几何链路验证（fit / rotate / 补偿）

云手机的相机 App 把节点 buffer 映射到预览区时**不保持 buffer 比例**：实测 640x480
的 buffer 被铺到 1080x1440，即 x 方向 ×1.6875、y 方向 ×3.0，纵向被拉伸 1.7778 倍。
所以竖屏 480x848 的视频直接送进节点，在屏幕上会被拉长成「0.33 的瘦条」。

camd 因此按 `content_w / content_h = 源比例 × ystretch` 来渲染：源内容先在 buffer 里
横向撑开，屏幕再纵向拉伸，两者相抵后用户看到的就是正确比例。ystretch 由
`G98_CAMD_YSTRETCH`（默认 1.7778）给出，是这台板子/这个镜像的实测常数。

- `fit=contain`（默认）：完整显示，左右补黑边。
- `fit=cover`：铺满整帧，超出部分居中裁掉（build_vf 里 scale+crop，rawvideo 必须仍是 640x480）。
- `fit=stretch`：直接拉伸到 640x480，不再补偿。
- `rotate=0/90/180/270`、`mirror`：转置/镜像后再做上面的几何。

逐环节比对（tests/verify_geometry.py）比较：源文件尺寸 → 节点 640x480 → 相机 App
SurfaceTexture/ImageReader 尺寸 → 截图里可见画面矩形，任何一环对不上就 FAIL。

```
python3 tests/verify_geometry.py wx1 /dev/video20 /root/camin/1795581891716.mp4 contain 1.7778
python3 tests/verify_geometry.py wx1 /dev/video20 /root/camin/1795581891716.mp4 cover   1.7778
```

2026-11-27 实测：480x848 / 24.05fps / 16.3s 的竖屏视频，contain 时屏幕可见区
814x1416（比例 0.575，源 0.566），cover 时铺满 1080x1416；两个模式都 PASS，且已并入
`tests/run_regression.sh` 的 geometry 阶段。

## 传感器栈（真机 SENC trace 回放）

云手机默认没有传感器（`dumpsys sensorservice` 报 `No Sensors on the device`、
`devInitCheck : -19`）。G98 用一个 Java HAL 把真机采集的传感器 trace 回放成 10 路虚拟传感器：

- `/vendor/etc/g98-sensors.dex`（`com.g98.sensors.SensorHalJava`，80 KB）
- `/vendor/bin/g98-sensors.sh` 启动器：首次运行把 `/vendor/etc/g98_sensors_trace.bin.gz`
  解压到 `/data/local/tmp/g98_sensors_trace.bin`（24.5 MB），之后 exec app_process
- `/vendor/etc/init/g98-sensors.rc`：`service g98-sensors ...` + `on boot start g98-sensors`
  （**必须 on boot 启动**，见文末「开机死锁」；再用 `on property:sys.boot_completed=1` 兜底）
- `/vendor/etc/vintf/manifest.xml` 必须声明 `android.hardware.sensors` AIDL v1 ISensors/default
  （以及 gnss v2 IGnss）

10 路传感器：Accelerometer / Gyroscope / Magnetometer / Rotation Vector / Gravity /
Linear Acceleration / Light / Proximity / Pressure / Step Counter，名字都带 `Fake` 前缀。

**关键坑**：manifest 是 servicemanager 在**进程启动时**读入并缓存的。改完 manifest 只重启
zygote 不够（那只会重启 system_server，servicemanager 仍用旧缓存），必须 `docker restart`
整个容器，否则日志里会看到
`servicemanager: Could not find android.hardware.sensors.ISensors/default in the VINTF manifest`
并回退到 HIDL sensors@2.1/2.0/1.0（都找不到）→ `devInitCheck -19`。

部署：`host/deploy/deploy_sensors_all.sh`（逐台拷文件 → 打 VINTF 补丁 → 启动 HAL），
已有容器要再 `docker restart` 一次让 servicemanager 重新读 manifest。
镜像 `deploy/Dockerfile` 已 COPY dex / rc / sh / trace.gz / vintf-manifest.xml，
新容器开箱即用；`build/wx-start.sh` 的 `ensure_sensors()` 对旧镜像容器做兜底补齐。

验收：`tests/verify_sensors.py` 每台检查 HAL 进程存活、AIDL 服务已注册、
`Total 10 h/w sensors`、10 个名字齐全、`devInitCheck` 非 -19。已并入 `tests/run_regression.sh`。
最近一次：**5/5 PASS**。

### 每台随机化（五台不能回放成同一个手机）

同一份真机 trace 直接回放会让五台云手机传感器**完全一致**（同一时刻、同一数值），
风控/多开场景一眼可辨。HAL 启动时读每台自己的种子文件
`/data/local/tmp/g98-sensors-seed.txt`（内容就是实例名 `wxN`，容器 `/data` =
宿主 `/srv/redroid/wxN`），做 FNV-1a 64 哈希得到 `devSeed`，再用它派生：

| 项目 | 范围 | 作用 |
| --- | --- | --- |
| `devShiftNs` | trace 时长的 `[0,1)` 随机 | 相位不同：各台回放 16 分钟 trace 的不同片段 |
| accel / gyro / mag / gravity / linear 偏置 | ±0.35 / ±0.03 / ±4µT / ±0.2 / ±0.2 | 静态值逐台不同 |
| pressure 偏置 | ±6 hPa | 同上 |
| `devLightScale` | 0.55–1.5 | 同一环境光下 lux 不同 |

日志：`grep -a "device variation" /data/local/tmp/sensors_java.log` 每台一行
（`id / seed / shiftMs / lightScale / accBias`）；`sample acc=` 是补偿后的真实事件采样。

实测（同一时刻五台加速度计，n=151 采样）：

```

wx2 -0.2750, -0.4641,  9.8732   shiftMs= 275821  lightScale=0.880
wx3 -0.0710, -0.5546,  9.9892   shiftMs=2323391  lightScale=0.851
wx4  0.1197, -0.2830,  9.9738   shiftMs=1922331  lightScale=1.310
wx5 -0.1874, -0.3911,  9.6049   shiftMs= 202857  lightScale=0.922
```

种子写入已内建在 `host/deploy/deploy_sensors_all.sh`（`G98_DATA_ROOT`，默认 `/srv/redroid`）
与 `build/wx-start.sh` 的 `ensure_sensors()`；手工兜底：


## 开机卡在启动阶段 → 相机 Activity 解析失败（2026-11-27 定位）

症状：容器重启后 `getprop sys.boot_completed` 一直为空，`cmd package resolve-activity --brief com.android.camera2` 返回
"No activity found"，相机 App 启动报 `Error type 3 / Activity class {com.android.camera2/...CameraLauncher} does not exist`，
e2e 卡在 `timeout waiting for streaming`。此时 `dumpsys package` 里 Activity/Filter 全都在，只是 PackageManager 还没完成启动。

两个独立诱因，都在"启动阶段就把 system_server 卡住"：

1. VINTF 里声明了 `android.hardware.gnss` AIDL HAL，但容器里没有对应服务。
   servicemanager 每秒重试 `Waited one second for android.hardware.gnss.IGnss/default`，system_server 停在启动。
   修法：manifest 只声明 `android.hardware.sensors`，删掉 gnss 条目（`cloudphone/host/g98-vintf-patch.sh` 已改）。
2. 假传感器 HAL 的 init rc 曾改成 `on property:sys.boot_completed=1`（想躲开旧 dex 的 FMQ
   `The write or read pointer has become misaligned` 报错），结果**反向死锁**：system_server 启动时同步等待
   `android.hardware.sensors.ISensors/default`，HAL 却要等 boot_completed 才起来 →
   `Waited one second for android.hardware.sensors.ISensors/default` 每秒刷、boot_completed 永远为空。
   修法（现行 rc）：改回 `on boot start g98-sensors`，并用当前 dex 实测 **boot=26s、10 路传感器、0 条 FMQ**；
   同时保留 `on property:sys.boot_completed=1` 作为幂等兜底。
   应急：容器卡在启动时 `docker exec <c> setprop ctl.start g98-sensors` 可在约 12s 内让开机继续走完。

排查命令：

```bash
docker exec wx1 getprop sys.boot_completed           # 必须为 1
docker exec wx1 sh -c "cmd package resolve-activity --brief com.android.camera2"
docker exec wx1 logcat -d -b all | grep -c "Waited one second for android.hardware.gnss"
docker exec wx1 logcat -d -b all | grep -c FMQ
```

配套加固：

- `g98-camd-prep.sh` 每次启动把 /dev/video20..31 统一 `chmod 666`（devtmpfs 默认 0600，容器里打开会 EACCES）；
  `cloudphone/deploy/tmpfiles-g98-video.conf` 提供同样的兜底。
- `docker restart wxN` 之后容器会丢 `vendor.camera.redroid.nodes` 属性，必须重跑 `/root/g98-camd-adopt.sh`
  （宿主 chmod + 重设属性 + 按正确顺序重启 provider/cameraserver）。
- 不要对相机 App 执行 `pm clear com.android.camera2`：会清掉已过引导的偏好，首次启动的"Remember photo locations?"
  引导页在这个镜像上会崩（`AndroidCameraAgentImpl ArrayIndexOutOfBounds`），相机再也打不开。
  恢复：`python3 /root/tests/seed_camera_prefs.py wx1 wxN`。

## 手机传感器实时同步（/m → /ms）

需求：把手机浏览器的真实传感器数据实时推给云手机，**人工开关、可勾选、默认全勾**；不支持的类型置灰。

链路：

```
手机浏览器 /ms 页（Generic Sensor API / DeviceMotion）
  └─ WebSocket /ws/sensor?name=wxN（dashboard，需登录 cookie）
      └─ /srv/redroid/<wxN>/local/tmp/g98-sensors-live.bin（容器内 /data/local/tmp/...）
          └─ /vendor/etc/g98-sensors.dex 的 live 通道（每 20ms 轮询）
              └─ AIDL ISensors → SensorService → 云机内的 App
```

实时文件固定 **180 字节、小端**：

| 偏移 | 类型 | 含义 |
| --- | --- | --- |
| 0 | int32 | magic `0x4739384C`（"G98L"） |
| 4 | int32 | ver = 1 |
| 8 | uint32 | mask，bit i = 1 表示第 i 个槽位用手机实时值 |
| 12 | int64 | wallMs（epoch 毫秒），HAL 只在 <1500ms 时采用 |
| 20 | float[40] | 10 槽 x 4 分量 |

槽位顺序（与 `SENSOR_SLOTS` 一致）：acc / gyro / mag / rv / grav / lin / light / prox / pressure / step。
mask 为 0 的槽位继续回放真机 trace；断开 WS 时 dashboard 会把 mask 写回 0（云机回落到内置数据）。

HAL 侧取证（`/data/local/tmp/sensors_java.log`）：

```
live mask=0x43 acc=1.25,-2.5,3.75 gyro=0.11,0.22,0.33 light=512.0,0.0,0.0
live type=1 v=1.25,-2.5,3.75
live mask=0x0
```

验收：`tests/verify_sensor_sync.py wx1`（WS 握手 → 文件 mask/数值 → HAL 日志 → 断开归零）已并入
`tests/run_regression.sh`。手动自测：`/ms?device=wx1&test=1&auto=1&k=<token>` 用合成正弦数组。

已知限制：

- "mask 归零"只在没有其它客户端时成立——控制台里还开着 `/ms` 的页面会持续推帧，测试需先关掉它。
- 10 路传感器同时注册时 logcat 偶发 `SensorService: Failed to read 2 events, currently 2 events available`
  （AidlSensorHalWrapper），事件会被丢弃；单路（如仅加速度计）无此问题。属于 HAL 事件包/队列写入语义问题，待后续修。
- Chrome 要求 https（或 localhost）才给 Generic Sensor；控制台 8443 入口可用，iOS 需在设置里允许"运动与方向"。

## 尺寸自适应：不再依赖 probe 结果（手机直播流尺寸错乱的修复）

问题：手机端「实时」把摄像头推给云机时，画面比例是错的（横过来、压扁或只有中间一条）。

根因：`/api/cam/start kind=stream` 到 camd 的那一刻，WHIP/RTSP 流通常还没出帧，
`probe_media()` 拿到空尺寸，`geometry()` 退回默认的 1280x960（DAR 1.333），
于是按「横屏源」排好了 buffer；而手机实际推上来的是竖屏（如 480x848），
buffer 里的内容就永远不对。上传的**文件**不会踩这个坑（文件在磁盘上，probe 一定成功）。

修复（`cloudphone/host/g98-camd.py`）：滤镜不再写死 content 尺寸，改成按输入帧动态计算：

- 先横向预拉伸 `scale=w='trunc(iw*ystretch/2)*2':h=ih`（抵消预览纵向拉伸 1.7778）
- contain：`scale=1280:960:force_original_aspect_ratio=decrease` + `pad=1280:960:(ow-iw)/2:(oh-ih)/2:black`
- cover：`scale=1280:960:force_original_aspect_ratio=increase` + `crop=1280:960:(iw-ow)/2:(ih-oh)/2`
- stretch：`scale=1280:960`
- JPEG 降级通道复用同一套逻辑（手机 canvas 分辨率变了也不会错）

这样无论源是 480x848、1080x1920 还是中途换分辨率，buffer 内容比例都等于「源比例」，
状态里 `geometry.dynamic=true` 表示源尺寸未知（直播流），`content_*` 只是占位值。

顺带修的卡顿：`kind=stream` 且节点还没有帧时，相机 App 必然打不开，原来会跑
一次约 25–38s 的全栈恢复（日志 `device0 not open after launch, recovering`）。
现在先等源出帧（最多 8s），仍无帧就只报「等待手机直播流（节点还没有帧）」，不再重启相机栈。

实测：竖屏 480x848 测试画面推 RTSP 后注入，buffer 内容 966x960（display_dar 0.566 = 源 0.566），
截图比例正常；上传 480x848 视频文件同样 contain 966x960、disp_dar 0.566。

## 静态帧降频（idle/image 写节点 30fps → 12fps）

`G98_CAMD_STATIC_FPS`（默认 12）：静态画面（idle 彩条、图片）仍按原样重复写，
但每帧 1280x960×1.5B ≈ 1.8MB，10 个节点 30fps 就是 ~550MB/s。实测降到 12fps 后
camd 自身 CPU 30% → 7%，provider 仍正常出图、看门狗 0（太低会触发 5s 捕获超时，别低于 ~10）。

## WebRTC 编码器不泄漏（观看端心跳 + 空闲回收）

现象：关掉控制台标签页后 `/root/ffmpeg ... rtsp://127.0.0.1:8554/wx1` 与容器内
`screenrecord` 会一直跑（实测残留 20 分钟、单条约 55% CPU），因为页面只在
`/api/rtc/start` 之后被动收流，没有任何「我还活着」的信号。

修复（`console3.board.py`）：

- 页面每 15s `POST /api/rtc/ping {name}`（桌面 `rtcStart` 与 `/m` 的 `connect()` 都加了
  定时器，`rtcStop` / `stopPC` 清掉）。
- `RTCSession.last_view` + `rtc_janitor` 线程每 10s 扫描，超过
  `G98_RTC_IDLE_TIMEOUT`（默认 45s）没有心跳就 `rtc_stop`，并写
  `/var/log/g98-actions.log`：`rtc reap idle wx1 after 49.9s without viewer`。
- `/whep/` 转发成功后刷新 `last_view` 并清零重连计数。
- `POST /api/rtc/ping` 返回 `{"ok": true, "alive": true}`。
- 额外限流：同一实例 60s 内超过 `G98_RTC_START_LIMIT`（默认 5）次 `start` 且没有观看端时
  直接返回错误，避免「WHEP 一直失败 → 页面无限重连 → 每轮起一条编码器」打满 CPU
  （日志 `rtc throttled wx1 (5 starts in 60s, no viewer)`）。

验收：`curl -X POST /api/rtc/start` 起流后不管它，约 45–55s 内被回收，
`ps | grep frame_pump` 为空，`/api/rtc/status` 返回空 `jobs`。

## WebRTC 懒启动：WHEP 来了才拉编码器（2026-11-27）

之前 `POST /api/rtc/start` 一被调用就起 `screenrecord + ffmpeg`（约 40–50% CPU），
即使没人订阅也照样编码；外部脚本/页面疯狂重连时只能靠限流和 15s 回收兜住。

改成「只登记、按需拉流」：

- `rtc_start(name, spawn=False)`：`/api/rtc/start` 只做清理（停旧会话、停旧的
  fMP4/MJPEG 管道）并返回 `{"ok": true, "pending": true, "url": "/whep/wx1"}`，
  **不动编码器**。日志 `rtc prepare wx1 (lazy, encoder starts on first WHEP)`。
- `_whep(name)`：收到浏览器真正订阅时调 `rtc_ensure(name)` 现拉编码器
  （复用存活会话，否则 `rtc_start(name, spawn=True)`），日志
  `rtc encoder up wx1 pid=... for incoming whep`。没人看 = 0% 编码 CPU。
- 服务端 WHEP 重试（关键）：编码器刚起时 mediamtx 还没注册 publisher，直接转发
  offer 会回 **404（WHEP 早于推流）**。`_whep` 现在对 404/502/503 以 200ms 间隔重试，
  最长 `G98_WHEP_READY_TIMEOUT`（默认 8s），浏览器完全无感，只慢首帧 0–2s。
  日志 `whep wx1 ready in N tries (code=201)`。

实测（wx1）：

| 场景 | 日志 | 结果 |
|---|---|---|
| 页面刷新 | `15:51:01 rtc prepare` → `15:51:03 rtc encoder up` → `15:51:03 whep ready in 1 tries (code=201)` | 首帧 <1s，页面 `30fps · 19ms` |
| 编码器被杀后自动重连 | `rtc reap idle`（`not st.alive()` 立即回收）→ `rtc prepare` → `rtc encoder up` | 页面自动恢复，无人工干预 |
| 无观看端 | 只 `rtc prepare`，`ps` 无 `screenrecord/ffmpeg` | 编码 CPU 0% |

404 重试的服务端验证：临时停掉 mediamtx，用 stub 让前两次 WHEP 回 404、第三次回 201，
`curl -X POST /whep/wx1` 得到 `code=201`、日志 `whep wx1 ready in 3 tries (code=201)`，
耗时 0.43s（2 次重试 × 0.2s）。验证完恢复 `systemctl start g98-mediamtx`。

## 长按手势（桌面控制台 + /m 移动端）

触摸链路原来是"点按走 `/api/tap`、拖动走 D/M/U 事件流"，**没有长按**：按住不放抬手会被当成一次点按，微信长按菜单、桌面壁纸/小部件菜单、拖动排序都出不来。

现在的规则（两处前端一致）：

| 手势 | 判定 | 下发 |
| --- | --- | --- |
| 点按 | 按下到抬起 < 380ms 且未移动 | `/api/touch a=t`（守护进程可用则走 WS），失败回落 `/api/tap` |
| 拖动 | 移动超过阈值（桌面 0.004、移动端 0.007） | D → M… → U（真实 MotionEvent 流） |
| **长按** | 按住 ≥ 380ms 且未移动 | 抬手时 `POST /api/longpress {name,fx,fy,dur}`，容器内执行 `input swipe x y x y dur`（原地按住） |

- 新增接口 `POST /api/longpress`：把 fx/fy 换算成像素、`dur` 夹到 400–5000ms，执行 `input swipe x y x y dur` 并写 `/var/log/g98-actions.log`（`longpress wx1 540 840 dur=900 rc=0`）。
- 按住期间画面加一圈提示描边（`img.holding`），松手才触发，不会误触。
- 为什么不用守护进程的孤立 D/U：实测 `D`→1.1s→`U` 不会被系统识别为按住（每次调用是独立注入，downTime 对不上），桌面壁纸菜单不弹；而原地 `input swipe` 能稳定触发。D/M/U 继续用于拖动（Settings 列表滑动实测前后截图 md5 不同）。
- 验证：模拟桌面端"按住 900–1000ms 再抬手"→ 桌面弹出 Wallpapers / Widgets / Home settings 菜单（截图 `lp5.png`）。

1. `keep_format=1` 时驱动直接忽略 `VIDIOC_S_FMT`（`vidioc_s_fmt` 里 `if (dev->keep_format || has_other_owners(...))` 分支），"先 keepf 再 ffmpeg" 永远改不动尺寸；

```
timeout 10 /root/ffmpeg -f lavfi -i testsrc2=size=WxH -t 4 -f v4l2 node &
sleep 2
/root/keepf node 1          # 趁 writer 还持有新格式
wait
```

## 前置摄像头「Camera error / -EBUSY」根因：HAL flush 死锁（2026-11-27）

现象：前置相机能打开一次，force-stop 后再开就弹「Camera error / Can't connect to the camera.」，
`dumpsys media.camera` 报 `Camera 1: initialize: Could not open camera session: Device or resource busy (-16)`；
宿主扫 `/proc/<provider>/fd` 可以看到 provider 一直持有 `/dev/video21`（fd 泄漏）。
logcat 只有 `V4L2Camera: flushBuffers:114: enter`，之后既没有返回也没有 `Closing camera device`。

根因（`aosp/libhardware13/modules/camera/3_4/v4l2_camera.cpp`）：
`dequeueRequestBuffers()` 在持 `in_flight_lock_` 的临界区内调用 `completeRequest()`（同步 upcall 到 provider
session）。App 被 force-stop 时 session 正在 close，这个 upcall 会阻塞；而 close 线程卡在
`Camera::flush()` → `flushBuffers()` 等同一把锁 → 死锁，`mBusy` 永为 true，v4l2 fd 不释放。

修复：
- `dequeueRequestBuffers()`：锁内只做 `DequeueRequest` 与计数，`completeRequest(request, 0)` 移到锁外。
- `flushBuffers()`：`tear_down_ = true` + `notify_all()` 唤醒等待的 dequeue 线程；`StreamOff()` 失败只
  `HAL_LOGW` 并继续返回 0，保证 `Camera::close()` 一定走到 `disconnect()` 释放 fd。
- `setupStreams()` 复位 `tear_down_ = false`；`v4l2_camera.h` 增加 `bool tear_down_ = false;`。

验证（wx1，前置后置各开关 3 轮共 6 次）：全部 `Device 1 is open`、`State: 2`，无 `Camera error` 对话框，
provider 只剩当前相机那一个 `/dev/video2x` 的 fd。部署：`bash _rehal7.sh` → `deploy_camera_all.sh`（五台 md5 4fff0f23）。

## 前置画面左右镜像：默认交给相机 App（真机行为，2026-11-27）

素材 `/root/camin/mirror_test.png` 是 1280×960、**左红 (254,0,0) / 右蓝 (0,0,255)**（ffmpeg crop
取点实测）。

两种策略的实测结果：
- `G98_CAMD_AUTOFRONT_MIRROR=1`（HAL 对前置节点预翻转）：相机 App 前置预览 = 左红右蓝
  （= 注入源原样）。因为 Android 相机 App 的 FRONT 取景器**自己**会做左右镜像，HAL 再翻一次
  正好把它抵消掉，看起来「不像镜子」；用户对照真机红米 K50 反馈「摄像头左右反了」。
- `G98_CAMD_AUTOFRONT_MIRROR=0`（当前默认）：相机 App 前置预览 = **左蓝右红（镜像）**，
  与真机自拍取景一致；后置节点不受影响，仍是左红右蓝（= 源）。

实现（`cloudphone/host/g98-camd.py`）：
- `AUTOFRONT = os.environ.get("G98_CAMD_AUTOFRONT_MIRROR", "0") == "1"` 与
  `node_is_front(node)`（节点号奇数即为前置：20+2(N-1)+1 = 21/23/25/27/29）。
- `NodeRouter.set_source()` 的 `mirror` 缺省（None）时取 `AUTOFRONT and node_is_front(node)`；
  显式传 `mirror` 时以参数为准。JPEG 降级通道同样带上 `JpegDecoder(..., mirror)` /
  `jpeg_vf(mirror)` / `jpeg_one_cmd(path, mirror)`，保证三条源路径行为一致。
- `cloudphone/host/g98-camd.service` 显式写 `Environment=G98_CAMD_AUTOFRONT_MIRROR=0`。
- 桌面控制台右栏「相机」「前置镜像」下拉：自动（跟随真机）/ 不翻转 / 翻转，`camFitOpts()`
  只有非自动时才带 `mirror`，其余情况交给 camd 按节点判定。
- 需要「注入什么就显示什么」时，可临时设环境变量为 1，或对单次注入传
  `POST /api/cam/start {..., "mirror": true}`。

验证（wx1，both=true 同时注入 mirror_test，相机 App 切到前置 Camera ID 1）：
- 后置预览 `bk.png`：左红右蓝（源方向，未镜像）。
- 前置预览 `fr4.png`：左蓝右红（镜像，真机自拍效果）。
- camd `/state`：`/dev/video20 mirror=false`、`/dev/video21 mirror=false`（默认不预翻转）。

注意：改镜像**不要重启 g98-camd**。它的 `ExecStartPost=g98-camd-adopt.sh` 会重启各容器的
provider/cameraserver，直接掐断正在使用的相机会话（微信报「Failed to obtain configurations」）。
单次注入用 `POST /api/cam/start` 的 `mirror` 字段覆盖即可。

## 前后摄切换：只能改 App 的偏好文件（2026-11-27）

现象：用户在移动端点「前置」，云手机里仍是后摄画面；相机 App 界面上也找不到切换按钮。

排查结论：
- 该镜像的相机 App 底部只有快门与 `...`，点开只弹出闪光灯 / 网格 / 画幅三个开关，
  **没有前后摄切换**（`dumpsys activity top` 里虽然有 `id/camera_toggle_button`，但不可点；
  底部栏 x=180/360/720/900/960 @y=2190 逐个点过，`Camera ID` 都不变）。
- `am start -a android.media.action.STILL_IMAGE_CAMERA --ez android.intent.extra.USE_FRONT_CAMERA`
  在这台镜像上不可靠：`true` 直接启动失败，`false` 与普通 `-n` 启动都停在前置。
- 真正的开关是 App 自己的偏好文件：
  `/data/data/com.android.camera2/shared_prefs/com.android.camera2_preferences_camera_PhotoModule.xml`
  里的 `<string name="pref_camera_id_key">0|1</string>`（0=后摄、1=前置）。主 prefs 文件里没有镜头键。

实现（`cloudphone/host/console3.board.py`）：
- `cam_lens_set(name, lens, launch=True)`：把 `g98-cam-lens.xml` 推到
  `/srv/redroid/<name>/local/tmp/` → `am force-stop` → 从 `dumpsys package` 读 uid →
  `cp` 到上面的偏好路径 → `chown uid:uid` + `chmod 660` → 可选 `am start` 重新打开相机。
- `cam_current_lens(name)` 直接 `cat` 偏好文件正则取值，比 `dumpsys media.camera`（整包 >120s）快得多。
- `POST /api/cam/lens {name, lens: front|back}`；`cam_do_start_camd` 在注入前比对
  `cam_node_is_front(node)`（节点号奇数=前置）与当前镜头，不一致就先切镜头再拉起 App，
  因此「点前置节点」= 云手机真的切到前置。
- `cam_device0_open()` 认 `Device [01] is open/closed`：切前置后打开的是 Device 1，
  只认 Device 0 会误判成没打开并触发一次多余的整栈恢复（实测多花 5–8 秒，日志里
  `open=False recovered=True`）。
- **「后置/前置」同时决定两件事**：① 手机浏览器调用哪颗真实摄像头（`getUserMedia facingMode`
  `environment`/`user`，`/cam` 页由查询参数 `facing` 初始化，`/m` 的 `camUrl()` 按所选镜头拼
  `&facing=user|environment`）；② 推流落到云手机的对应节点（前置=奇数节点 /dev/video21 等）。
  手机浏览器要在 HTTPS（:8443，自签证书需点「继续」）下才能拿到摄像头权限。
- **手机摄像头的前后切换是热的，不重启云手机 App**：`/cam` 页把翻转逻辑收成
  `switchFacing(nf)`（`videoSender.replaceTrack`，推流不中断），自有翻转按钮与宿主页
  `postMessage({cmd:'facing'})` 走同一条路径；`/m` 点前置/后置时如果预览已打开，只发
  `postMessage`，**不重载 iframe、不调 `/api/cam/lens`**（因为 `both:true` 已让前后两个节点
  吃同一条流，App 不用动）。只有首次「打开摄像头」或确实要换云手机镜头时才需要重启 App。
- 注入时的镜头比对先读一次真实偏好（`cam_current_lens`）再决定是否切换：缓存为空时
  以前每次注入都会 force-stop 一次相机 App（等于每次注入都重启），实测同镜头连续注入

## 源静默时保持出帧（hold last frame）+ MAX_SILENCE 30s（2026-11-27）

## HAL 小尺寸 stream config：原生 1280x960 采集、出帧缩放（2026-11-27）

为什么：微信人脸验证走旧版 Camera API1 且写死 640x480。media_profiles 修好后仍报
`E Camera2-Parameters: set: Requested preview size 640 x 480 is not supported`；
而且 API1 会同时开 640x480 预览 + 320x240 数据回调，被 `setupStreams` 的"多流必须同几何"
检查直接 -EINVAL（`capture 640x480 vs stream 1 320x240`）。

约束：v4l2loopback `keep_format=1` 忽略 S_FMT，节点只有 1280x960，`SetFormat` 请求小尺寸
必然失败，所以**不能只加 metadata**，必须"声明小尺寸 + 仍按原生采集 + 出帧缩放"三处一起改
（仓库 `cloudphone/hal/camera3_4/`，与 `aosp/libhardware13/modules/camera/3_4/` 同步）：

1. `format_metadata_factory.cpp`：stream config = 设备尺寸 ∪ {640,480}/{320,240}
   （仅当小于原生且 `small_w*native_h == small_h*native_w` 同比例），时长复用原生尺寸。
2. `v4l2_camera.cpp setupStreams`：采集永远用 `GetFormatFrameSizes(YUV420)` 里最大面积的尺寸
   （1280x960）；多流几何不同不再 `return -EINVAL`，改为按输出缓冲各自缩放。
3. `v4l2_wrapper.cpp`（`V4L2Wrapper::DequeueRequest`）：YUV420 输出与 BLOB/JPEG 输出在
   尺寸不一致时先 `arc::ImageProcessor::Scale`（libyuv I420Scale）再交织 NV12 / 编码 JPEG
   （JPEG 编码器把编码尺寸当源 stride，不先缩放会剪切错位）。

验证：
- `dumpsys media.camera`：fmt 33/34/35 各有 320x240、640x480、1280x960，时长均 33333333ns。
- 自研真实 API1 客户端探针 `cloudphone/tests/api1probe/`（Cam1Small.java → cam1small.dex）：
  `ActivityThread.systemMain()` + 反射 `Application.attach` 解决 `Camera.cameraInit` 的 NPE；
  camera 0/1 均 supportedPreview=[320x240 640x480 1280x960]，640x480 预览 frames>0、
  bytes=460800（=640*480*3/2）。回归入口 `tests/verify_api1_preview.py`。
  探针注意：先 `am force-stop com.android.camera2`（前台相机 App 持设备会让
  `Camera.open` 抛 "Fail to connect to camera service"）；首帧在相机 App 刚被杀后可能
  超过 4s 才来，所以 RESULT 延迟 10s、runner 等 22s，避免假失败。
- 位级对照：640x480 的 API1 输出 == 1280x960 的 API1 输出最近邻缩小到 640x480，
  mean_abs_diff=0.00 / max=0（_measure_bands.py），证明缩放正确且未引入方向/色彩变化。
- 注意：API1 预览回调是 **NV12**（ffmpeg 必须 `-pix_fmt nv12`，误用 yuv420p 会出现紫色伪影）；

## 注入流「像真机」：传感器噪声 / AE 呼吸 / 帧抖动（2026-11-28）

背景：微信人脸活体在资源齐全后仍不认脸。相机链路本身已健康，差异只剩「画面统计特征」：
真实手机推来的每一帧都有传感器散粒噪声、AE/AWB 缓慢漂移、帧间隔抖动；而 camd 的静态图
与静默保持帧是逐字节完全相同的画面，节拍也是完美等间隔——这是「翻拍/贴图」检测最廉价的
特征。改造目标：让下游拿到的流在统计上像一台真机摄像头，而不是一张循环播放的图片。

### 实现（cloudphone/host/g98-camd.py）

- 动态源（video / rtsp / jpeg）：build_vf 在 fps 之后追加 ffmpeg 滤镜
  noise=alls=N:allf=t+u（每帧时域噪声，G98_CAMD_GRAIN 默认 6）与
  eq=brightness=0.02*sin(2*PI*t/19)（AE 呼吸，G98_CAMD_AE_BREATH / AE_PERIOD）。
  全部在 ffmpeg 里做，Python 侧零开销。
- 静态源（image / idle）：render_static_set 一次渲染多帧带噪画面
  （G98_CAMD_STATIC_VARIANTS 默认 6，idle 只 2 帧），写线程轮流发送，肉眼是「颗粒在动」。
- AE 呼吸（静态源）：breath_step(ts) 把当前亮度档量化为整数级（±5/255），
  breath_table(step) 用 bytes.translate 做 C 级亮度查表（1.2MB Y 平面 <1ms）。
  档位每 ~2s 才变一次，变时把整组变体重算并缓存（breath_frames），之后每帧零成本；
  idle 不做呼吸（占位彩条不值得 6×1.8MB 内存）。
- 帧抖动：写线程周期乘 1±G98_CAMD_FRAME_JITTER（默认 0.18），帧间隔不再等间隔。

### 实测（板子，10 节点）

- idle 全节点：camd RSS 62MB、CPU 40 ticks/8s（约 5%），written 稳定。
- image 注入（astronaut.png，2 节点）：连续 12 帧 distinct=5，首尾帧 60000 个 Y 采样中
  54391 个不同（约 90%），meanY 109.34 → 110.34 → 115.34 → 116.33（±5 级呼吸），
  written 12.2fps、errors 0。
- rtsp（testsrc2 30fps 推流）：每帧 100000 个 Y 采样中约 83300 个不同，噪声逐帧变化。
- 成本：仅 image 节点付呼吸缓存（6 帧 ×1.8MB ≈ 11MB/节点）；idle 与 rtsp 不额外占内存。

### 测试

cloudphone/tests/verify_texture.py（已并入 run_regression.sh，hold 之前）：注入 image 后断言
帧间有差异（>500/60000 采样不同）、meanY 随时间漂移（>0.5）、written ≥6fps 且 errors=0，
最后切回 idle 断言仍在出帧。

### 注意

关掉这些效果可做对照实验：G98_CAMD_GRAIN=0、G98_CAMD_AE_BREATH=0、
G98_CAMD_FRAME_JITTER=0、G98_CAMD_STATIC_VARIANTS=1，然后 daemon-reload + restart。
A/B 已量化：仅关闭呼吸，10 个 idle 节点的 CPU 从 411 ticks/8s 降到 42。

## 移动网页限帧与「伪 135fps」：rawvideo CFR 在 90k tbr 下复制帧（2026-11-28）

- 推流端是 dashboard 的 /cam 移动网页，不是第三方 App。网页原先 getUserMedia 没有 frameRate、WHIP RTCRtpSender 也没限帧；已统一 `frameRate:{ideal:30,max:30}`，发送端设 `maxFramerate=30`、`maxBitrate=2500000`，首次打开与前后摄切换均生效。页面显示实际发送 fps/kbps；部署后需关闭旧页面再重新打开。
- **后续证伪了“手机实际发 135fps”的判断**：camd source_frames 高增量来自板子 ffmpeg 复制帧。低探测参数下 VP8 被报为 `90k tbr/90k tbn`，rawvideo 默认 CFR 以此为目标；同流对照中默认 rawvideo 输出 31409 帧、`dup=31388`，加 `-fps_mode passthrough` 后仅 128 个真实解码帧。管道背压后，伪输出在 /state 中表现为约 145fps。
- 修复：仅实时 RTSP rawvideo 分支增加 `-fps_mode passthrough`，保留已解码帧及原始 PTS，不让 muxer 补帧；同时加 `-nostdin`，防止脚本中的 ffmpeg 消耗 `bash -s` 后续命令。实时链仍不叠 noise/AE/fps 重采样，静态/文件源拟真逻辑不变。
- 部署验证：两路活动 ffmpeg argv 均含 passthrough，written 约 29.6fps；另抽查 107 个直通帧，107 个 PTS 全部唯一，分辨率恢复到 720×1280。source_frames 仍会随真实手机 PTS 波动，不能再单独用它推断网页采集帧率。
- 回归：tests/verify_mobile_fps.py 检查网页采集/发送约束，tests/verify_live_clean.py 检查实时滤镜及 passthrough/nostdin。重启 camd 要同时清理遗留的 cam-wx1 ffmpeg 子进程，再执行 prep + adopt；否则旧复制帧 reader 可能继续占用源。

## 公网查看相机/云手机画面：HLS + Basic 口令（2026-11-29）

目标：把板子上 mediamtx 的画面通过 OTA 服务器暴露到公网，但必须带 key。
公网入口是 `https://sales-ck.kuaihuoyun.com`（Kong 网关 → prod 192.168.6.251:80 →
systemd-socket-proxyd → 127.0.0.1:3001 的 `/opt/workphone-ota/server.py`）。

链路与实测：

- **prod 访问不到板子**（`curl http://192.168.5.111:8888|8889|8099` 全 000），板子能到 prod。
  因此用板子发起的反向 SSH 隧道：`/etc/systemd/system/g98-cam-tunnel.service`
  `ssh -N -i /root/.ssh/g98_tunnel_ed25519 -p 32409 -R 127.0.0.1:18888:127.0.0.1:8888 root@192.168.6.251`，
  `Restart=always`，已 `enable --now`；prod 上 `ss -ltnp` 可见 `127.0.0.1:18888`。
- **nginx 在 prod 上是死的**（`nginx.service` inactive，80 端口由 `systemd-socket-proxyd 127.0.0.1:3001`
  持有），所以加 nginx 反向代理没有用，必须改 OTA 的 Python 服务。
- `/opt/workphone-ota/server.py` 增加 `/cam/` 前缀代理（`CAM_PREFIX`/`CAM_UPSTREAM=('127.0.0.1',18888)`/
  `CAM_KEY_FILE=/etc/g98/cam.key`）：先校验 `Authorization: Basic base64(g98:<key>)`，不匹配返回 401 +
  `WWW-Authenticate: Basic realm="g98 cam"`；匹配则透传到隧道并加 `Access-Control-Allow-Origin: *`、
  `Cache-Control: no-store`。原文件已备份为 `server.py.bak-cam-<时间戳>`，`py_compile` 通过后
  `systemctl restart workphone-ota`。
- 公网地址（**HLS，延迟约 2–6 秒**）：
  - 云手机屏幕（dashboard RTC 会话）：`https://sales-ck.kuaihuoyun.com/cam/wx1/index.m3u8`
  - 手机推送的相机画面（camd 注入源）：`https://sales-ck.kuaihuoyun.com/cam/cam-wx1/index.m3u8`
  - 其它 path 同理：`/cam/<mediamtx path>/index.m3u8`
- 实测：无凭据 401；带凭据取到 master playlist、media playlist 与分片
  （`53572ad38d88_video1_seg24.mp4` 200 / 71604B），说明隧道 + 鉴权 + HLS 全链通。

为什么不是直接暴露 `http://192.168.5.111:8889/`（mediamtx 的 WebRTC 播放页）：WHEP 需要
WebRTC 媒体端口（`webrtcLocalUDPAddress: :8189`），七层 HTTPS 反代搬不动，除非在公网侧
放 UDP 中继或启用 `webrtcLocalTCPAddress`；HLS 是纯 HTTP，能直接走 OTA 的 443。

安全约束：key 只出现在私有 `/etc/g98/cam.key`（0600）与用户手中；mediamtx 只读暴露通过 `/cam/`，
HLS 是只读的，无法借此推流。mediamtx 自身的匿名 publish 仍只在内网可达。

### 外网把画面推上来：/camctl 页面 + JPEG 通道（2026-11-29）

HLS 只解决“看”，手机在外网把自己的摄像头画面“推”进云手机还需要页面本身可访问。

- **必须用 HTTPS 打开页面**：`/cam` 页靠浏览器 `getUserMedia` 采集手机摄像头，而
  `getUserMedia` 只在安全上下文可用（`https://` 或 `localhost`）。内网
  `http://192.168.5.111:8099/cam` 是非安全上下文，Chrome 直接拒绝授权，所以公网 HTTPS 入口
  反而是这条通道的前提。
- **隧道加了第二个端口**：`g98-cam-tunnel.service` 的 ExecStart 现在同时有
  `-R 127.0.0.1:18888:127.0.0.1:8888`（mediamtx HLS）与
  `-R 127.0.0.1:18889:127.0.0.1:8099`（dashboard）。
- **server.py 代理（v2）**：`/camctl` → 板子 `/cam`（保留查询串）；`/api/cam/` 只放行白名单
  `frame,start,stop,state,status,orient,geom` → 板子 8099；转发时注入
  `Cookie: g98k=<dashboard token>`（prod `/etc/g98/dash.token`，0600，值等于板子
  `/etc/g98/cloudphone.token`），因为 dashboard 的 `/api/cam/frame` 要求 cookie 鉴权。
  `/api/cam/file`、`/api/cam/files`、`/api/cam/qr`、`/ws/`、`/whip/`、`/whep/` 一律不代理。
- **原始 server.py 没有 do_POST**（`SimpleHTTPRequestHandler` 只实现 GET/HEAD），不补的话
  `POST /api/cam/frame` 直接 501，页面会以为通道坏了；v2 补了 `do_POST` 走同一套
  `_rewrite_path` 分发。
- 页面地址：
  `https://sales-ck.kuaihuoyun.com/camctl?device=wx1&node=/dev/video20&facing=user&jpeg=1`
  加 `jpeg=1` 强制跳过 WebRTC/WHIP（外网没有 UDP 8189，WHIP 必然失败），直接走 10fps JPEG：
  页面把 1280×960 画布编码成 JPEG `POST /api/cam/frame` → dashboard → camd `kind=jpeg`
  逐帧解码成 YU12 写进 v4l2 节点。
- 实测：带凭据页面 200、无凭据 401；`POST /api/cam/frame` 返回 `{"ok":true}`；
  `GET /api/cam/status` 透传正常；`/api/cam/files` 404（白名单外）。
- 代价与注意：JPEG 单帧约 100–250 KB × 10 fps ≈ 1–2.5 MB/s 上行，移动网络会吃力；
  且把节点切成 `jpeg` 会顶掉原来的 rtsp 注入，用完要 `/set` 回
  `rtsp://127.0.0.1:8554/cam-wx1`。
- 重放补丁：`cloudphone/deploy/ota_cam_proxy.py <key>`（v2，幂等；v1 只有 HLS 时会就地升级）。
