## 一、gralloc / 图形栈

### 1. 64 位和 32 位的 device 函数槽位完全不同

| ABI | free | allocate | get_backing_store |
|---|---|---|---|
| 64 位 | 112 | 120 | 128 |
| 32 位 | 56 | 64 | 72 |

**坑**：只按 64 位偏移打补丁，32 位容器里所有分配都走原生函数，wrapper 完全不生效，而且不报错。

### 2. `memcpy` 结构体大小写死 408 会越界

32 位 `gralloc_module_t` 是 **256 字节**，64 位是 408。写死 408 在 32 位读越界 152 字节，导致随机崩溃。

```c
memcpy(&HMI, g_real, sizeof(HMI));   // ✅ 用 sizeof
memcpy(&HMI, g_real, 408);           // ❌ 32 位越界
```

### 3. memfd 不是 GPU 可导入的缓冲区

用 `memfd_create` 造 YUV 缓冲区给 Android 用 → allocator 服务的 fd 从 7 涨到 **32768**，整个系统（包括显示）瘫掉。

**教训**：Android 图形栈要的是 dma-buf，不是 memfd。这个实验路径后来被彻底禁用（`is_yuv_fmt()` 强制返回 0）。

### 4. 把裸内存当结构体指针用会 NULL 解引用

```c
static uint8_t s_alone[512];
wrapper_dev_t *wd = (wrapper_dev_t*)s_alone;   // ❌ 字段全是垃圾值
```

后果：显示黑屏，`screencap` 返回 0 字节。改成 `static wrapper_dev_t s_alone;` + 空指针保护后解决。

### 5. cros gralloc 只支持 `YUV_420_888 (0x23)`

test 过的格式：

| 格式 | cros 支持 |
|---|---|
| `YUV_420_888` (0x23) | ✅ rc=0 |
| NV12 / YV12 / RGBA 等 | ❌ |

handle 结构（32 位，numFds=2 numInts=34）：

```
ints[3]=640 stride   ints[4]=640 cstride
ints[8]=307200 Y size  ints[12]=153600 UV size
ints[16]=640 width     ints[17]=480 height
ints[18]=0x3231564E (NV12)
```

### 6. mapper 版本才是真凶（最重要）

系统 vintf manifest 只声明 `mapper@2.1`，而相机 HAL 的 `HandleImporter` 只找 **2.0 / 3.0 / 4.0**。

试过的三条路，全部失败：

| 尝试 | 结果 |
|---|---|
| 只加 `<fqname>@2.0::IMapper/default</fqname>` | lshal 仍显示 X（不可用） |
| 把 mapper 库复制成 2.0 期望的文件名 | lshal 仍显示 X |
| 插入完整 `<hal>` 块（含 `<version>2.0</version>`） | **系统崩溃，`lshal` 段错误** |

**教训：vintf manifest 里声明一个没有对应实现的 HAL 版本，会让 hwservicemanager 直接崩，系统起不来。改之前一定要备份，改完要能 SSH 回滚。**

### 7. 删除 mapper 库验证问题，会得出错误结论

为了确认"是不是 mapper 的问题"，把 mapper impl 库删了 → 日志出现 `mMapperV4, mMapperV3 and mMapperV2 are all null!`

我据此判断"mapper 2.0 结构性缺失"，**这是错的**。恢复库之后这个错误就消失了，说明 mapper 2.0 其实可用（通过 -2.1 覆盖机制）。

**教训：破坏性验证会污染结论。删除前先想清楚"恢复后怎么重新验证"。**

### 8. 自定义 gralloc wrapper 根本不会被 external camera HAL 调用

logcat 实测计数（相机跑到 `formatConvert` 那一次）：

```
f_perform      = 0
f_lock_ycbcr   = 0
f_lock         = 0
G98BACKING     = 0（HAL 进程）
formatConvert  = 1
```

V4L2 侧 strace 里连一次对输出缓冲区的 `mmap` 都没有。

**原因**：external camera HAL 走 `HandleImporter`（HIDL mapper），不碰 legacy `gralloc_module_t`。**我们所有 hook 都是 legacy 模块接口，external HAL 一个都不用。**

## 二、摄像头设备与 V4L2

### 9. RTSP 发布者和相机 HAL 抢同一个设备

`/dev/video10` 同时被 MediaMTX 的 ffmpeg 和 Android camera HAL 打开 → `VIDIOC_S_FMT failed: Device or resource busy`。

**解决**：video10/11 专门留给 Android camera，video12/13 给串流。

### 10. 板子上没有真实摄像头

`/dev/video0-3` 全是编解码器：

```
video0  rkvdec            硬件视频解码器
video1  rockchip-rga      2D 图形加速器
video2  rk3568-vpu-dec    视频解码
video3  rk3588-vepu121-enc 视频编码
```

`lsusb` 里没有任何摄像头。**要真实画面只能插 USB 摄像头或手机推流。**

### 11. 手机推流的路径前缀

手机推 `rtmp://host/live/face` → MediaMTX 里的路径是 **`live/face`**，不是 `face`。

拉流写成 `rtsp://host/face` 会 404。这个坑卡了两轮。

### 12. ffmpeg 低延迟参数会跟 v4l2 输出打架

```bash
# ❌ 输出 0 帧："Output file is empty, nothing was encoded"
ffmpeg -fflags nobuffer -flags low_delay -re -i rtsp://... -f v4l2 /dev/video12

# ✅ 去掉低延迟参数就正常
ffmpeg -rtsp_transport tcp -i rtsp://... -vf "scale=640:480,fps=25" -f v4l2 /dev/video12
```

## 三、Android 容器（redroid）

### 13. `wrap.` 前缀的 LD_PRELOAD 注入不生效

redroid 的 init **不支持 `wrap.` 前缀**（那是 Android 模拟器的机制）。

**解决**：直接改 `/vendor/bin/hw/cam-provider.sh`（它本来就是 shell 脚本启动器，不是二进制）。

### 14. FUSE 没挂载导致相机 App 崩溃

`Storage.<init>` NullPointerException。

**解决**：`ro.hw_timeout_multiplier=10` 给 FUSE 挂载留更多时间。

### 15. `docker -p` 端口映射会失败

```
iptables ... Extension tcp revision 0 not supported
```

**解决**：不用 `-p`，直接访问容器 IP + `service.adb.tcp.port`。

### 16. `service.adb.tcp.port` 重启就丢

容器重启后清空。**解决**：`adb-ports.service`（oneshot，等 `sys.boot_completed=1` 后再 setprop）。

### 17. oneshot 服务显示 inactive 但进程在跑

`camstream` / `adb-ports` 是 `Type=oneshot`，后台进程起完就退出，systemd 状态是 `inactive (dead)`。

**教训：体检脚本要检查功能（流是否 200），不能只看 `systemctl is-active`。**

### 18. `screencap` 会挂起

redroid 的 `screencap` 在设备繁忙时阻塞 60 秒以上。

**后果**：给面板加实时截图的方案彻底失败（4 个 `<img>` 各卡 60 秒，页面无法使用），已回退。

### 19. 相机 App 连接成功率约 1/6

调试时不能在循环里死等。**解决**：用 `ndkcam5`（原生测试程序）稳定跑通 `configureStreams`，比 App 可靠得多。

### 20. 相机设备方向被报成 EXTERNAL

```
CAM_Camera2OneCamMgr: No back-facing camera found
```

App 最终会 fallback 继续连接（`Not sure where camera is facing to.`），不阻塞。

### 21. 相机特性声明缺失

原镜像只有 `android.hardware.camera` 一个特性，**缺 `android.hardware.camera.any`**（现代 App 优先检查这个）。

**解决**：往 `/system/etc/permissions/` 放一个 XML：

```xml
<permissions>
    <feature name="android.hardware.camera.any" />
    <feature name="android.hardware.camera.autofocus" />
    <feature name="android.hardware.camera.flash" />
    <feature name="android.hardware.camera.front" />
    <feature name="android.hardware.camera.external" />
</permissions>
```

效果：特性数 1 → 6。

## 七、当前结论

**我们和社区的关键差异：**

| HAL 类型 | 缓冲区路径 | 我们的 wrapper 能否生效 |
|---|---|---|
| `camera.v4l2`（legacy 3_4） | `gralloc_module_t` 直调 | ✅ 能 |

**方向：做 legacy 相机 HAL（`camera.v4l2` 或 antmicro/android-camera-hal）。**

## 八、第 200 轮：legacy HAL 可行性核查

### 核查结论

| 项 | 结果 |
|---|---|
| `LegacyCameraProviderImpl` 是否在镜像里 | ❌ 逐库扫描，没有 |
| `camera.v4l2.so` 是否在镜像里 | ❌ 没有（`/system/lib/hw` 只有一个 HIDL ashmem mapper） |
| `lockYCbCr` 是否可 LD_PRELOAD 拦截 | ❌ `nm -D` 显示既非导出也非导入，**静态编译进库** |
| 网上是否有 arm64 Android 13 预编译 `camera.v4l2.so` | ❌ 搜不到 |
| redroid 社区是否有人做出可用方案 | ❌ 无（#574 / #621 / ERSTT#7 全部悬空） |

### 相机 HAL 进程实测（pid 87）

```
pid 87 = android.hardware.camera.provider@2.7-external-service
  /proc/87/maps 里有: gralloc.cros.so  gralloc.g98.so  gralloctypes.so

说明：我们的 gralloc 模块**确实被加载进了相机 HAL 进程**，
但所有 hook（perform / lock / lock_ycbcr / get_backing_store）在
YUV 路径上调用次数都是 0。
```

### 为什么 legacy HAL 能绕过问题

```
external camera HAL:  buffer_handle_t → HandleImporter → HIDL IMapper@2.0/2.1 → ✗
legacy camera HAL:    buffer_handle_t → gralloc_module_t->lock_ycbcr  → ✓（我们控制）
```

**但 legacy 路线需要两个镜像里没有的组件：**

1. `camera.v4l2.so`（AOSP `hardware/libhardware/modules/camera/3_4`）
2. legacy camera provider（`camera.provider@2.4-legacy-impl.so` + service）

两者都需要 **AOSP 源码树 + 交叉编译环境**（约 200GB、数小时构建）。
本机（Windows，无 WSL）和板子（无外网、无源码）都不具备。

### 决策

**相机这项在现有资源下无法推进。** 需要以下任一：

| 选项 | 需要什么 | 预期 |
|---|---|---|
| A. 换镜像 | 别人编译好的、带 legacy camera HAL 的 redroid 镜像 | 高（我们 wrapper 已就绪）|
| B. 提供构建机 | Linux + AOSP 13 源码 + 200GB | 中高 |
| C. 放弃 App 内相机 | —— | 用 WebRTC 串流方案 |

### 其余系统状态（不受影响）

```
4 台云手机运行中，微信已装
相机特性已补全（1 → 6 个，含 camera.any）
摄像头串流 cam0/cam1 = 200，推流守护自动运行
```

## 第 113 轮：发现相机请求的是 YV12，不是 YUV_420_888

### 关键发现

从 logcat 抓到相机的实际分配请求：

```
W_ALLOC_ENTER 640x480 fmt=0x32315659 usage=0x20130   <- 0x32315659 = YV12
G98ALLOC 640x480 fmt=0x32315659 usage=0x20130 -> 0x130
```

**相机 HAL 请求的是 YV12（0x32315659），不是 YUV_420_888（0x23）。**

而 cros gralloc **只支持 0x23，拒绝 YV12**（第 58 轮验证过格式矩阵）。

### 因果链

```
相机请求 YV12
  -> 旧 wrapper: is_yuv_fmt(YV12) = false
    -> 直接转给 cros allocate
      -> cros 拒绝（只支持 0x23）
        -> 分配失败，返回无效 handle
          -> HAL 拿到坏缓冲区
            -> HandleImporter::lockYCbCr 返回 BAD_VALUE (error 3)
              -> formatConvert 拿到全 0
```

**这解释了为什么我们所有 gralloc hook 都没被调用：分配在 cros 那一步就失败了。**

### 本轮实现

新增 `yuv1fd_alloc()`：用 RGBA 载体伪装成单 fd 的 YUV 缓冲区

```c
long need = w * h * 3 / 2;                   // YUV420 字节数
int  ch   = (need + w*4 - 1) / (w*4);       // RGBA 需要的行数
wd->real_alloc(dev, w, ch, 0x1 /*RGBA*/, usage, &carrier, &stride);
nh->numFds = 1;  nh->data[0] = carrier_fd;
```

`is_yuv_fmt` 扩展为接受 0x23 / YV12 / NV12 / NV21；`f_lock_ycbcr` 增加 mmap 路径。

### ⚠️ 未完成验证

6 台实例满载后相机 App 连接成功率接近 0（连续 10 次 ext=0，伴 binder 事务超时）。
m1 本身健康，只是负载下的偶发超时。**下一轮需在低负载下验证**（临时停 m3-m6）。

## 第 114 轮：YV12 单 fd 分配器跑通（关键突破）

### 验证到的成果

低负载测试（停掉 m2-m6，只留 m1）抓到了完整日志：

```
G98YUV1 try0 640x180 fmt=0x1 usage=0x130 -> rc=0
G98YUV1 640x480 fmt=0x32315659 -> fd=8573 carrier=640x180 (1 fd, 460800 bytes)
G98YUV1 try0 640x180 fmt=0x1 usage=0x130 -> rc=0
G98YUV1 640x480 fmt=0x32315659 -> fd=8575 carrier=640x180 (1 fd, 460800 bytes)
```

**相机现在能拿到有效的单 fd YV12 缓冲区了**（之前是分配失败）。

### 修复过程中的两个问题

**问题 1：载体分配失败 rc=-22**

第一次尝试时 `yuv1fd_alloc` 直接透传 `usage=0x20130`，cros 拒绝。
正常路径里有 `usage & ~USAGE_HW_CAMERA_WRITE`，我漏了。

修复：剥离相机专用 usage 位 + 三级 fallback：

```c
struct { int w, h, fmt, usage; } tries[] = {
    { w, ch, 0x1, usage & ~USAGE_HW_CAMERA_WRITE },  /* 成功 */
    { w, ch, 0x1, 0 },
    { w, ch, 0x4, 0 },
};
```

**问题 2：缓冲区泄漏导致 rc=-28 (ENOSPC)**

```
G98YUV1 try0 ... rc=-28
G98YUV1 all carriers failed
```

6620 次分配 × 460 KB = **3 GB** 没有释放 —— 我的代码根本没实现 free 路径。

修复：`yuv1_free()` 从注册表摘除、关闭 fd、释放 handle、
并调用 cros 的 `real_free` 释放载体本身；挂到 `w_free` 开头。

### 当前状态

```
单 fd YV12 分配：✅ 已验证 rc=0
载体使用率：640x480 -> 640x180 RGBA（正好 460800 字节）
泄漏：✅ 已修复
lock_ycbcr 调用：❌ 仍是 0（未验证到最后一步）
formatConvert：❌ 本次未触发
```

### 为什么还没验证到出帧

相机 App 在这台机器上连接成功率极低（约 1/12），
而且经常出现 `mCurrentFocus=null`（窗口没焦点，点击无效）。

低负载那次跑了 12 轮才成功 1 次，抓到 3718 条 YUV1 日志后
就因泄漏耗尽资源（rc=-28）。修复泄漏后需要再碰一次成功的连接。

### 下一步

1. 反复重试直到相机 App 连上（预期 1-2 分钟内会有一次成功）
2. 成功时检查 `LOCKYCBCR_ENTER` 是否 > 0
3. 若 > 0，说明 mapper 这次接受了单 fd YV12 缓冲区，路线通了
3. 若仍为 0，说明 mapper 还有其他校验，需要看 `lockYCbCr error` 是否变化

## 第 115 轮：发现窗口焦点陷阱 + 回滚有问题的模块

### 重要发现 1：窗口要按键才有焦点

m1 上相机 App 一直 `mCurrentFocus=null`，点击全部无效。
发送一次按键后：

```
before:   mCurrentFocus=null
after HOME: mCurrentFocus=Window{... com.android.camera2/com.android.camera.CameraLauncher}
```

**窗口一直存在，但需要输入事件才会被聚焦。**
这是 redroid 容器在长时间运行后的状态异常，用 `input keyevent` 可以唤醒。

### 重要发现 2：新 YV12 模块有回归问题

A/B 实测（m1 新模块 vs m2 旧模块）：

| 实例 | 模块大小 | 相机 App 状态 |
|---|---|---|
| m1 | 18856 B（新，含 YV12） | **卡在 Splash Screen** ❌ |
| m2 | 17024 B（旧，稳定） | Splash Screen EXITING ✅ |

**单 fd YV12 分配虽然成功了（rc=0），但返回的 handle 会让相机 App 卡死。**

推测原因：App 拿到 1 fd 的 YV12 handle 后，
在某个环节（可能是 GraphicBuffer 封装或显示路径）阻塞。

### 已回滚

从 m2 复制稳定模块（17024 B）覆盖 m1，重启验证：

```
m1 模块 = 17024 B（与 m2-m6 一致）
相机 App Splash Screen 卡死计数 = 0
boot=1
```

### 保留的成果

**YV12 发现本身是正确且有价值的**（已记录在踩坑文档）：


## 第 117 轮：YV12 → 0x23 格式翻译（新方案）

### 思路

之前两种做法都失败：

| 方案 | 结果 |
|---|---|
| 让 YV12 走我们的单 fd 载体 | 分配成功但相机 App 卡死 |
| 直接让 cros 分配 YV12 | cros 拒绝（只支持 0x23） |

**新方案：把 YV12 请求在 wrapper 层直接翻译成 0x23，用 cros 原生分配。**

```c
if (fmt == 0x32315659 /*YV12*/ || fmt == 0x3231564E /*NV12*/ || fmt == 0x3132564E /*NV21*/) {
    g98log("G98XFMT translate fmt=0x%x -> 0x23", fmt);
    fmt = 0x23;
}
```

这样缓冲区是 cros 原生的 2-fd NV12，**不是伪造的 handle**，
相机 App 不会卡死（已实测确认 splash 不再卡住）。

要在多次尝试中碰上一次成功的 configureStreams 才能看到 G98XFMT 日志。

## 第 121 轮：发现相机栈死锁

### 决定性证据

在 ndkcam5 运行期间执行 `dumpsys media.camera`：

```
Stream[0]: Output
  Consumer name: ImageReader-640x480f23u3m8-3462-0
                （f23 = format 0x23，u3 = usage 3，m8 = maxImages 8）

*** SERVICE 'media.camera' DUMP TIMEOUT (10000ms) EXPIRED ***
```

**CameraService 的 dump 请求被阻塞 10 秒超时。**

### 这意味着什么

正常情况 `dumpsys media.camera` 是毫秒级的。超时说明：

1. CameraService 持有某个锁，而锁的持有者被阻塞
2. 阻塞发生在 HAL 层（configureStreams 之后、process_capture_request 期间）
3. 典型的循环等待：

```
HAL 等待 Camera3 提供输出缓冲区
  <- 同时 Camera3 等待 HAL 从 process_capture_request 返回
    -> 死锁
```

### 为什么之前没发现

之前只看 logcat，HAL 打完 `configureV4l2StreamLocked: start V4L2 streaming` 就没了，
我们以为是"没调用"，实际上是**卡在那里不返回**。

`dumpsys` 超时是第一个能证明"阻塞"而不是"未调用"的证据。

### 完整失败模型（更新）

```
1. 相机枚举、openCamera              OK
2. ImageReader 创建 (0x23, 8 buffers) OK
3. configureStreams                   OK
4. V4L2 S_FMT / REQBUFS / QBUF        OK
5. Camera3 请求第一个输出缓冲区        <- 卡住
6. HAL process_capture_request         <- 卡住
   互相等待 -> 死锁
7. dumpsys media.camera 超时 10s
8. formatConvert 永不执行
```

### 下一步（明确方向）

1. 用 `kill -QUIT` 或 `debuggerd` 抓取 HAL 进程（87）的调用栈
2. 看它卡在哪个函数（大概率在 gralloc allocate 或 mapper lock）
3. 如果卡在 allocation，说明我们的 wrapper 有阻塞问题
4. 如果卡在 mapper，说明 mapper 内部死锁

**这是 121 轮来第一次有明确的"死锁"证据，而不是猜测。**

## 第 122 轮：抓到了完整调用栈，定位到真正的死锁点

### 三个关键进程的调用栈

**1. 相机 HAL（pid 87）** —— 空闲等待

```
"ExtCamOut" sysTid=4147
    #04 ExternalCameraDeviceSession::OutputThread::waitForNextRequest()
    #05 ExternalCameraDeviceSession::OutputThread::threadLoop()
```

HAL 没死锁、没卡在 gralloc —— 它在**等 Camera3 发请求**。

**2. cameraserver / Camera3（pid 2809）** —— 卡在 dequeueBuffer

```
"C3Dev-110-ReqQu" sysTid=4767
    #06 BpGraphicBufferProducer::dequeueBuffer
    #07 Surface::dequeueBuffer
```

Camera3 的请求队列线程**阻塞在从 ImageReader 的 BufferQueue 取缓冲区**。

**3. allocator 服务（pid 90）** —— 完全空闲

```
线程只有 3 个: allocator@2.0-s / HwBinder:90_1 / HwBinder:90_2
无任何 gralloc / allocate 帧
```

分配器根本没收到请求。

### 完整死锁链

```
ndkcam5 的 ImageReader BufferQueue
  <- Camera3 dequeueBuffer 阻塞在这里（binder 调用不返回）
    <- 所以 Camera3 永远不调用 HAL 的 process_capture_request
      <- 所以 HAL 的 ExtCamOut 永远在 waitForNextRequest()
        <- 所以 formatConvert 永不执行
          <- 0 帧

allocator 服务全程空闲 —— 分配请求根本没到它那里
```

### 这个结论的意义

**卡点不在我们的 gralloc wrapper，也不在 mapper，也不在相机 HAL。**

而在 **Camera3 ↔ 应用 ImageReader 的 BufferQueue 通信**。

这是 Android framework 层在 redroid 容器里的问题，
和我们改了 120 轮的所有东西（gralloc / mapper / camera HAL）**都无关**。

### 为什么之前一直误判

| 之前的判断 | 实际情况 |
|---|---|
| mapper 拒绝 handle | 根本没走到 mapper |
| Camera3 不提交 buffer | 对，但原因是 dequeueBuffer 阻塞 |
| dumpsys media.camera 超时 = CameraService 死锁 | 是 BufferQueue 卡住导致的连锁 |

### 现在可以确定

```
1. 相机 HAL / V4L2 / gralloc / mapper 都没问题
2. 问题在 Camera3 -> ImageReader BufferQueue 的 dequeue
3. 这一层在 redroid 容器里工作不正常
4. 任何在 gralloc/mapper/HAL 层面的修改都无法解决
```

### 唯一可能的解决方向

| 方向 | 说明 |
|---|---|
| 换镜像 | 不同 redroid/AOSP 版本 BufferQueue 行为可能不同 |
| 用 legacy camera HAL | 走不同的 BufferQueue 路径（camera.v4l2 + provider@2.4-legacy）|
| 放弃 App 内相机 | 用 WebRTC 串流方案 |

## 九、2026-11-19/20：App 内相机（Camera2）与外部画面注入

### 1. 一广告 BLOB（拍照）相机就变 0 台
`format_metadata_factory.cpp` 里 `qualified_formats.size()==0` 会直接 `-ENODEV`。板子的 v4l2loopback 只枚举 YU12，而 `GetQualifiedFormats` 只认 YUYV/MJPEG → qualified 恒空。
**修**：给 BLOB / IMPL_DEFINED 加特判，回退到 `V4L2_PIX_FMT_YUV420`；否则报 `Failed to get all frame sizes for format 877807426`。

### 2. tag 值别凭记忆
界面弹 "Camera error / Can't connect"，日志是 `Invalid request settings` + `Rejected request tag 0x10002`。0x10002 **不是** fps range，而是 `ANDROID_CONTROL_AE_LOCK`。查 `CameraMetadataTag.aidl` 确认。
**修**：`menu_control_options.h` / `slider_control_options.h` 的 `IsSupported()` 恒 true（这些控件对 HAL 无效果，不该让整条请求失败）。

### 3. YUV_420_888 客户端 buffer 是 NV12，不是 I420
直拷会出现绿/品红照片。
**修**：Y 直拷，色度按 `chroma[row*width + col*2] = U; +1 = V` 交错写，`SetDataSize(w*h*3/2)`。

### 4. 客户端 buffer 的 dma-buf fd 可能是只读
`mmap(PROT_WRITE)` → `EACCES`；`/proc/self/fd/N` 重开 O_RDWR 也被拒；gralloc `lock` 报 `-22 Invalid handle`（因为没 registerBuffer）。
**教训**：`HandleImporter_custom.cpp` 的 `importBuffer` 空实现是取巧，正规做法是 mapper importBuffer+registerBuffer。

### 5. 换 v4l2 生产者后必须同时重启 provider 和 cameraserver
否则 `initializeImpl: unable to initialize device: Device or resource busy (-16)`（exclusive_caps=Y 节点还被旧 fd 占着）。只重启 provider 不够，cameraserver 仍记得 `Camera provider 'legacy/0-0' has died`。

### 6. 板子没有 X11，Windows 也没有能用的 ffmpeg
`ffmpeg-static/bin/ffmpeg` 是 aarch64 ELF，Windows 跑不了。实时抓屏只能用 PowerShell GDI + TCP 推流。

### 7. docker exec 里嵌套引号会被吞
多次 `grep` 无输出就是这个原因。一律「本地写脚本 → scp → `sh /tmp/x.sh`」，并给每个 `docker exec` 套 `timeout`。

### 8. docker cp 读不到 /sdcard（FUSE）
照片要走真实路径 `/data/media/0/Pictures/`；`uiautomator dump` 写 `/sdcard/ui.xml` 也会失败，改 `/data/local/tmp/`。

### 9. adbd 的 TCP 端口
redroid 里改 `service.adb.tcp.port` 后必须 `stop adbd; start adbd`（同一个 `sh -c` 里），端口按 `5554+n`（m6=5560）。当前实测还是没监听，临时用 `docker exec` 直接控制。

### 10. 内存
6 台容器已占 ~15GB/15.9GB，相机 App 冷启动 2–2.5 分钟且常被 lmkd 杀掉。测试前先 `stop vendor.camera-provider-2-7-ext` 并少开容器。

## 十、2026-11-21/22：VM 路线与 m7 单容器

### 1. VM 线为什么走不通

- QEMU 10.0.13 构建没有 `virtio-gpu-gl-pci`，宿主也没有 virglrenderer；Mali-G610 是 platform device，无法 VFIO 直通。guest 只能 ANGLE/pastel 软渲。
- guest 没有 `/dev/video*`、没有 `/lib/modules`；板子又是 MIPI 摄像头（非 USB UVC），QEMU 没有 UVC 模拟，VM 内相机无路径。
- VM 根挂载是 `/dev/vda ext4`，`/sys/block` 有 `vd*`，会触发 riskcheck 的 mount/block 检查；SELinux 仍 `Disabled`。
- 写 `ro.crypto.state=encrypted` 会让 `vdc cryptfs enablefilecrypto` 失败并无限重启（`Status(-8, EX_SERVICE_SPECIFIC): '0: '`），不能靠 build.prop 伪造加密状态。

### 2. VM 属性补丁的可复用点

- `ro.hardware` 默认值在 `/system/bin/init` 文件偏移 `0x18FB2`（十进制 `102322`）的字符串 `unknown`；改成 `mt6983`+NUL 后 `getprop ro.hardware` 生效。
- `build.prop` 可补 flavor/id/fingerprint/`ro.boot.verifiedbootstate`/`flash.locked`/`veritymode`/`selinux`；VM 启动参数也可以补 `androidboot.*`。
- 改 qcow2 前必须先杀 qemu，否则 `qemu-nbd --connect` 会因镜像锁失败；标准流程：`qemu-nbd --connect=/dev/nbd0 --format=qcow2 /root/vm/vm1.qcow2` → `mount -t ext4 /dev/nbd0 /mnt/vm1` → 修改 → `sync/umount` → `qemu-nbd --disconnect`。

### 3. m7 镜像/启动的坑

- 基础镜像 Entrypoint 是 `["/init","qemu=1","androidboot.hardware=redroid"]`；`docker run` 的 Cmd 会追加在后面。必须加 `--entrypoint /init`，否则 `ro.boot.hardware` 仍是 `redroid`，属性全部不生效。
- 改 `ro.hardware=mt6983` 后，`hw_get_module()` 会找 `hwcomposer.mt6983.so`、`camera.mt6983.so`；镜像里只有 `.redroid.so`，必须复制同名文件，否则 SurfaceFlinger 报 `failed to open framebuffer device`、相机 0 路。
- rt:13 基础镜像只有 camera provider 2.7 external；2.7 注册会报 `must be in VINTF manifest`，手工加 manifest 又会报 `Duplicated interface entry` / `Duplicated manifest.hal entry` / `Duplicated major version`。正确路线是 m6 文件系统里的 2.4 legacy provider。
- Docker `--device /dev/video14:/dev/video10` 的 rename 在 Android ueventd 重建 `/dev` 后不生效；直接使用宿主 `video14/15`，并设置 `vendor.camera.redroid.nodes=/dev/video14,/dev/video15`。
- `vendor.camera.redroid.nodes` 首次生效前节点权限是 `660 root:44`，cameraserver uid 1047 打不开；必须 `chmod 666 /dev/video14 /dev/video15`。
- 同一 v4l2loopback 节点同一时刻只能一个进程打开；测试相机前先 `am force-stop com.g98.camtest`，然后同时 `setprop ctl.stop vendor.camera-provider-2-4-legacy` + `ctl.stop cameraserver`，再按 start 顺序重启。只重启一个会 `Device or resource busy (-16)` 或 `Function not implemented (-38)`。
- `camera.redroid.so` 的 `setupStreams` 先尝试 YUV420，ffmpeg 生产者必须 `-pix_fmt yuv420p`；`yuvj420p`/MJPEG 会 `S_FMT failed: Device or resource busy`。

### 4. riskcheck 伪装

- 需要同时满足：`ro.debuggable=0`、`ro.secure=1`、`ro.build.type=user`、`ro.build.tags=release-keys`、`ro.boot.verifiedbootstate=green`、`flash.locked=1`、`veritymode=enforcing`、`crypto.state=encrypted`、`adb_enabled=0`，以及避开 redroid/angle/pastel/qemu/goldfish 等字符串。
- riskcheck 还会看 `/proc/1/cgroup`、`/proc/version`、`/proc/cmdline`、`/sys/block`、`/proc/self/attr/current`、`/sys/fs/selinux/policy` 和 root 挂载行；只改 build.prop 不够。
- m7 的透明伪装：`/fake/enforce`（内容 1）bind 到 `/sys/fs/selinux/enforce`，空 `/fake/block` bind 到 `/sys/block`，`/fake/attr` 和 `/fake/mounts` 由 `risk-watch.sh` 在 riskcheck 新 pid 出现时 bind 到 `/proc/<pid>/attr/current` 和 `/proc/<pid>/mounts`。
- `getenforce` 仍显示 `Disabled`；riskcheck 只看 `enforce` 字符串，所以 score 能到 0，但这**不是真实 SELinux enforcing**。

### 5. m7 最终验证

- `sys.boot_completed=1`、`ro.hardware=mt6983`、`ro.boot.hardware=mt6983`、`ro.build.flavor=houji-user`、`ro.build.fingerprint=Xiaomi/houji/houji:13/TKQ1.221114.001/V14.0.9.0.TMCCNXM:user/release-keys`。
