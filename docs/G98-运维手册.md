## 2. 启动新实例

```bash
N=5; ADB=5559
docker rm -f m$N 2>/dev/null
mkdir -p /srv/redroid/m$N
docker run -d --name m$N --privileged --network bridge \
  --cap-add SYS_NICE --ulimit rtprio=99 --device /dev/dri \
  -v /srv/redroid/camcfg/cam0-external_camera_config.xml:/vendor/etc/external_camera_config.xml:ro \
  -v /srv/redroid/m$N:/data \
  g98/redroid-panthor-rt:13 qemu=1 androidboot.hardware=redroid \
  ro.hardware.gralloc=g98 ro.hw_timeout_multiplier=10

# 必须：替换 gralloc
docker cp /root/gralloc.g98.so    m$N:/vendor/lib64/hw/gralloc.g98.so
docker cp /root/gralloc.g98.32.so m$N:/vendor/lib/hw/gralloc.g98.so
docker exec m$N chmod 644 /vendor/lib64/hw/gralloc.g98.so /vendor/lib/hw/gralloc.g98.so

# ADB 端口（不要用 -p，本板 iptables 缺 nf_tables tcp/DNAT 扩展）
docker exec m$N setprop service.adb.tcp.port $ADB
```

**注意**：`ro.hw_timeout_multiplier=10` 必需，否则 FUSE 外部存储挂载失败，
相机 App 会在 `Storage.<init>` 抛 NullPointerException 直接崩溃。

**启动时序**：`sys.boot_completed=1` 之后还要等约 60-120 秒，
直到 `ls /storage/emulated/0` 能列出内容，系统才真正可用。

## 3. 摄像头串流

一键拉起：

```bash
bash /root/cam-bringup.sh
```

开机自启已配置：`systemctl enable camstream.service`

访问地址：

| 协议 | 地址 |
|---|---|
| WebRTC（浏览器） | http://192.168.99.50:8889/cam0 、 /cam1 |
| HLS | http://192.168.99.50:8888/cam0/index.m3u8 |
| RTSP（VLC） | rtsp://192.168.99.50:8554/cam0 |

设备分配：
- `/dev/video10, 11` → 保留给 Android 相机 HAL（不要挂 RTSP 发布者）
- `/dev/video12, 13` → 串流 cam0 / cam1

**重要**：RTSP 发布者读取同一个 v4l2 设备会导致相机 HAL 的
`VIDIOC_S_FMT` 报 `Device or resource busy`，所以必须分开。

## 4. 已知限制

### 4.1 App 内相机无法出帧

相机 App 可以打开相机（`cam=1`）、HAL 可以 configureStreams、
V4L2 推流可以启动、`formatConvert` 会被调用，
但 `HandleImporter::lockYCbCr` 经 mapper@2.1 返回全 0 的 ycbcr 结构，
导致 `formatConvert: unsupported flexible yuv layout`，HAL 报严重错误。

已确认：
- mapper 对 YUV handle 不调用我们模块的 `get_backing_store`（28 次查询全是 RGB 形态）
- mapper 对 YUV handle 不调用我们的 `lock_ycbcr`（计数 0）
- handle 的 ints 不会在 HIDL 传递中丢失（RGB 的 35 个 ints 完整保留）

这是 redroid 图形栈 mapper 实现对 gralloc0 YUV handle 支持不完整所致，
位于系统库内部，不在自定义 gralloc wrapper 范围内。

### 4.2 板子无外网

`curl baidu/github/google/apkpure` 全部返回 000。无法下载 APK。
微信需要手动提供 APK 后 `adb install` 或 `pm install`。

## 5. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 显示黑屏、screencap 0 字节 | allocator 服务 fd 耗尽 | 重启容器；确认没有 memfd 泄漏 |
| 所有分配失败 | 同上 | `ls /proc/$(pidof android.hardware.graphics.allocator@2.0-service)/fd \| wc -l` 检查 |
| 相机 App 崩溃在 Storage.java | FUSE 未挂载 | 加 `ro.hw_timeout_multiplier=10` |
| 相机 HAL 报 VIDIOC_S_FMT busy | 有第二个进程读同一 v4l2 设备 | 检查 `fuser -v /dev/video10` |
| `docker: veth pair operation not supported` | 重启后缺 veth 模块 | `modprobe veth` |
| 容器启动但 ADB 不可用 | 端口未设置 | `setprop service.adb.tcp.port` |

## 7. 补充：ADB 端口不持久

`service.adb.tcp.port` **不会**在容器重启后保留，每次重启需要重设：

```bash
for n in 1 2 3 4; do
  port=$((5554+n))
  docker exec m$n setprop service.adb.tcp.port $port
  docker exec m$n sh -c "stop adbd; start adbd"
done
```

建议写进启动脚本，或在 `/data/local.prop` 里固化。

### 相机问题交接（给后续接手的人）

**最终确认的失败链：**

```
相机 App / ndkcam5 打开相机
  -> CameraService::connect  OK
  -> HAL configureStreams    OK（ext=5）
  -> HAL V4L2 推流启动        OK
  -> Camera3 提交 capture request
    -> HandleImporter::lockYCbCr
      -> mapper@2.0（-2.1 覆盖机制，已验证可用）
        -> 返回 BAD_VALUE (error 3)
          -> formatConvert 拿到全 0 的 ycbcr
            -> HAL 报严重错误，0 帧
```

**已排除（都有实测证据）：**

| 项 | 证据 |
|---|---|
| gralloc 格式路由 | 0x23 已正确走 cros |
| memfd 泄漏 | redroid 路径已禁用，fd 稳定 7 |
| mapper 缺失 | mapper@2.0 可用（无 all-null 错误） |
| perform 未实现 | 已实现 + 部署，但从未被调用 |
| lock_ycbcr 未实现 | 探针验证 rc=0、指针正确，但从未被调用 |
| handle ints 丢失 | RGB 的 35 个 ints 完整保留 |

**关键未解点：**

```
mapper 的 registerBuffer 被调用（4 次），
但 lock_ycbcr / lock / perform / get_backing_store
在 YUV 路径上全部 0 次调用。
```

意味着 mapper 在 `registerBuffer` 之后、`lock` 之前就失败了。

**下一步建议的调试方向：**

1. 在 `f_register` 里返回一个非零错误，观察 HAL 是否报不同的错误码
   —— 这能确认 mapper 是否真的依赖 registerBuffer 的返回值
2. 用 `strace -f -e trace=ioctl,mmap` attach 到 HAL 进程，
   看 lock 阶段实际做了什么系统调用
3. 对比一台正常的 Android 设备，看 mapper 对 YUV handle 的处理差异
4. 最直接：换一个带完整 gralloc2/gralloc4 mapper 的 Android 镜像

### 建议的替代方案（如果相机是硬需求）

| 方案 | 可行性 | 工作量 |
|---|---|---|
| 换 redroid 镜像（带 gralloc4 mapper） | 高 | 低（只需替换镜像） |

## 第 103 轮：HAL 依赖分析（新方向评估后放弃）

### 本轮设想

尝试用 LD_PRELOAD 拦截 `HandleImporter::lockYCbCr` 这个 C++ 方法，
直接返回我们自己构造的 ycbcr 描述，绕过 mapper 的校验。

### 调查结果

```
HAL 入口: /vendor/bin/hw/android.hardware.camera.provider@2.7-external-service
          11824 字节 ELF 32 位 ARM 可执行文件（小型启动器）

它 NEEDED 的库（含实现在内）:
  libbinder, libcamera_metadata, libhidlbase, liblog,
  libtinyxml2, libutils, libc++, libc, libm, libdl
  + 7 个厂商私有库（名字被脱敏）
```

### 为什么放弃这条路

`HandleImporter::lockYCbCr` 的调用发生在**厂商私有库内部**，
它可能是内联展开或被 LTO 优化掉，不是可拦截的动态符号。

而且：

| 障碍 | 说明 |
|---|---|
| 符号不可见 | readelf 里查不到 lockYCbCr 的导入/导出 |
| 私有库脱敏 | 7 个 NEEDED 库名无法直接定位实现 |
| 32 位 ABI | 需要 32 位 ARM 编译环境构造正确的 C++ 对象 |
| 风险 | 拦截失败会导致相机服务崩溃，影响现有稳定状态 |

## 第 113 轮：发现相机请求的是 YV12，不是 YUV_420_888

### 关键发现

从 logcat 抓到相机的实际分配请求：

```
W_ALLOC_ENTER 640x480 fmt=0x32315659 usage=0x20130   <- 0x32315659 = YV12
G98ALLOC 640x480 fmt=0x32315659 usage=0x20130 -> 0x130
```

**相机 HAL 请求的是 YV12（0x32315659），不是 YUV_420_888（0x23）。**

而 cros gralloc **只支持 0x23，拒绝 YV12**（第 58 轮验证过格式矩阵）。

### 因果链

```
相机请求 YV12
  -> 旧 wrapper: is_yuv_fmt(YV12) = false
    -> 直接转给 cros allocate
      -> cros 拒绝（只支持 0x23）
        -> 分配失败，返回无效 handle
          -> HAL 拿到坏缓冲区
            -> HandleImporter::lockYCbCr 返回 BAD_VALUE (error 3)
              -> formatConvert 拿到全 0
```

**这解释了为什么我们所有 gralloc hook 都没被调用：分配在 cros 那一步就失败了。**

### 本轮实现

新增 `yuv1fd_alloc()`：用 RGBA 载体伪装成单 fd 的 YUV 缓冲区

```c
long need = w * h * 3 / 2;                   // YUV420 字节数
int  ch   = (need + w*4 - 1) / (w*4);       // RGBA 需要的行数
wd->real_alloc(dev, w, ch, 0x1 /*RGBA*/, usage, &carrier, &stride);
nh->numFds = 1;  nh->data[0] = carrier_fd;
```

`is_yuv_fmt` 扩展为接受 0x23 / YV12 / NV12 / NV21；`f_lock_ycbcr` 增加 mmap 路径。

### ⚠️ 未完成验证

6 台实例满载后相机 App 连接成功率接近 0（连续 10 次 ext=0，伴 binder 事务超时）。
m1 本身健康，只是负载下的偶发超时。**下一轮需在低负载下验证**（临时停 m3-m6）。

## 第 114 轮：YV12 单 fd 分配器跑通（关键突破）

### 验证到的成果

低负载测试（停掉 m2-m6，只留 m1）抓到了完整日志：

```
G98YUV1 try0 640x180 fmt=0x1 usage=0x130 -> rc=0
G98YUV1 640x480 fmt=0x32315659 -> fd=8573 carrier=640x180 (1 fd, 460800 bytes)
G98YUV1 try0 640x180 fmt=0x1 usage=0x130 -> rc=0
G98YUV1 640x480 fmt=0x32315659 -> fd=8575 carrier=640x180 (1 fd, 460800 bytes)
```

**相机现在能拿到有效的单 fd YV12 缓冲区了**（之前是分配失败）。

### 修复过程中的两个问题

**问题 1：载体分配失败 rc=-22**

第一次尝试时 `yuv1fd_alloc` 直接透传 `usage=0x20130`，cros 拒绝。
正常路径里有 `usage & ~USAGE_HW_CAMERA_WRITE`，我漏了。

修复：剥离相机专用 usage 位 + 三级 fallback：

```c
struct { int w, h, fmt, usage; } tries[] = {
    { w, ch, 0x1, usage & ~USAGE_HW_CAMERA_WRITE },  /* 成功 */
    { w, ch, 0x1, 0 },
    { w, ch, 0x4, 0 },
};
```

**问题 2：缓冲区泄漏导致 rc=-28 (ENOSPC)**

```
G98YUV1 try0 ... rc=-28
G98YUV1 all carriers failed
```

6620 次分配 × 460 KB = **3 GB** 没有释放 —— 我的代码根本没实现 free 路径。

修复：`yuv1_free()` 从注册表摘除、关闭 fd、释放 handle、
并调用 cros 的 `real_free` 释放载体本身；挂到 `w_free` 开头。

### 当前状态

```
单 fd YV12 分配：✅ 已验证 rc=0
载体使用率：640x480 -> 640x180 RGBA（正好 460800 字节）
泄漏：✅ 已修复
lock_ycbcr 调用：❌ 仍是 0（未验证到最后一步）
formatConvert：❌ 本次未触发
```

### 为什么还没验证到出帧

相机 App 在这台机器上连接成功率极低（约 1/12），
而且经常出现 `mCurrentFocus=null`（窗口没焦点，点击无效）。

低负载那次跑了 12 轮才成功 1 次，抓到 3718 条 YUV1 日志后
就因泄漏耗尽资源（rc=-28）。修复泄漏后需要再碰一次成功的连接。

### 下一步

1. 反复重试直到相机 App 连上（预期 1-2 分钟内会有一次成功）
2. 成功时检查 `LOCKYCBCR_ENTER` 是否 > 0
3. 若 > 0，说明 mapper 这次接受了单 fd YV12 缓冲区，路线通了
3. 若仍为 0，说明 mapper 还有其他校验，需要看 `lockYCbCr error` 是否变化

## 第 116 轮：窗口焦点恢复工具

### 问题

长时间/反复操作后，redroid 的窗口会失去焦点（`mCurrentFocus=null`），
此时所有 `input tap` / `input text` 都无效 —— 用户会以为"云手机卡死了"。

### 解决方案

`/root/g98-wake.sh`：

```bash
/root/g98-wake.sh 1      # 恢复 m1 的焦点
/root/g98-wake.sh all    # 恢复全部 6 台
```

内部流程：

```
1. input keyevent KEYCODE_WAKEUP   唤醒屏幕
2. input keyevent 82               MENU 键，强制窗口聚焦
3. input keyevent KEYCODE_HOME     回到桌面（可选）
4. dumpsys window 报告当前焦点
```

### 实测

```
# 重启 m1 后立即检查
焦点 = null

# 跑 g98-wake.sh 1
m1 -> Window{9cdc164 u0 com.android.camera2/...}   <- 恢复
```

**注意**：如果 wake 无效，说明该实例状态异常，需要 `docker restart`。

### 使用场景（运维手册已记录）

| 症状 | 处理 |
|---|---|
| ADB 点击没反应 | `bash /root/g98-wake.sh <n>` |
| WeChat 启动后不响应点击 | 同上 |
| wake 也无效 | `docker restart m<n>` |
